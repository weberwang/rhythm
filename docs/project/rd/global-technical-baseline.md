## 1. PRD 需求理解

### 1.1 产品目标

Rhythm 的目标不是做“睡眠结果展示器”，而是做一个本地优先、行为闭环导向的作息管理产品。首发验证链路是：

`今晚提醒 -> 睡前收尾 -> 次日反馈 -> 原因标签 -> 恢复建议 -> 周复盘`

### 1.2 目标用户

- 主要用户：长期晚睡但愿意调整作息的移动端用户
- 首发优先：20-35 岁、iOS 真机用户
- 次要用户：跨时区用户、后续可能扩展的轮班用户

### 1.3 核心场景

- 首次进入后快速形成“可用状态”
- 晚间从提醒或首页进入睡前模式并执行收尾动作
- 次日理解偏离与恢复建议
- 周期性复盘趋势并决定是否升级订阅

### 1.4 范围内功能

- 睡眠数据接入、手动补录、目标作息、睡前提醒、今日页、热力图、周报
- 账号同步、会员体系、恢复计划、稳定度解释
- 国际化、权限降级、数据来源标识、隐私与删除导出能力

### 1.5 明确不做

- 医疗诊断与治疗型能力
- 社区、内容陪伴、复杂游戏化
- 首发即覆盖轮班复杂场景
- 在当前阶段输出模块级实现文档和页面级视觉文档

## 2. 假设前提与待确认项

### 2.1 假设前提

- 首发以 `iOS` 真机作为主要验证面，`Android` 暂不作为首发阻塞项。
- 匿名本地使用默认开放，登录与云同步属于增强能力。
- 首发采用本地优先架构，核心闭环在离线或弱网环境下仍可使用。
- 健康原始数据读取优先在端内完成，云端默认只同步必要业务数据与派生结果，不同步全部原始健康明细。
- 当前仓库已有平台工程与依赖声明，但 `lib/` 业务代码骨架缺失，应视为“尚未完成 bootstrap”的状态。

### 2.2 待确认项

- 是否需要在首发阶段接入远程配置、A/B 实验与灰度开关。
  影响章节：埋点、监控与运营支持；实施计划与里程碑
- 订阅权益是否需要后端做二次校验与服务端快照落库。
  影响章节：后端协作与接口契约要求；数据与安全方案
- Google / Apple 登录是否统一通过 Supabase Auth 承接，还是保留独立身份提供商绑定层。
  影响章节：Flutter 客户端详细技术方案；后端协作与接口契约要求
- 首发是否要求推送型运营触达，还是仅本地通知。
  影响章节：后端协作与接口契约要求；埋点、监控与运营支持

## 3. 业务流程与页面范围

### 3.1 主流程

1. 首次激活：欢迎 -> 登录/匿名选择 -> 健康授权或手动路径 -> 目标作息 -> 提醒策略 -> 今日页
2. 晚间执行：通知/小组件/今日页 -> 睡前模式 -> 今晚状态 -> 收尾动作
3. 次日反馈：今日页查看结果 -> 标记原因 -> 恢复建议 -> 查看趋势
4. 周期复盘：洞察页查看周报 / 稳定度 / 历史趋势 -> 决定是否升级

### 3.2 异常流程

- 健康授权拒绝：直接转手动补录
- 自动数据缺失：显示“当前判断不完整”，允许补录或稍后重试
- 登录失败或弱网：保持本地可用，延后同步
- 通知权限关闭：保留手动进入睡前模式
- 订阅恢复失败：不影响基础功能，权益状态需可重试校正

### 3.3 粗粒度能力范围

当前阶段只定义粗粒度能力，不做模块冻结：

- `app-shell`：应用入口、导航、公共壳层、全局错误与启动分发
- `onboarding-activation`：首启、匿名/登录选择、授权与初始设置
- `sleep-data-core`：睡眠记录、来源标记、补录、修正、同步桥
- `today`：昨晚结果、今晚目标、快捷入口、恢复卡
- `bedtime`：睡前模式、状态选择、轻量动作、提醒承接
- `calendar`：热力图、单日详情、趋势查询
- `insights`：周报、稳定度、恢复详情、付费承接
- `profile-settings`：账户、同步、隐私、订阅、通知、小组件设置

### 3.4 页面关系

推荐保留五个一级入口：

- 今日
- 日历
- 睡前
- 洞察
- 我的

睡前页可同时作为底部一级入口与通知深链目标页，避免晚间关键入口被隐藏。

## 4. 总体技术架构

### 推荐方案

采用“`本地优先 + 按能力分层的 Feature DDD-lite + 云端增强同步`”架构：

- 表现层：`hooks_riverpod` + `go_router`
- 应用层：按 feature 组织用例、状态聚合、流程编排
- 领域层：`freezed` 值对象、实体、仓储接口、业务规则
- 数据层：本地 `drift`、安全存储、外部插件 adapter、远端 sync gateway
- 启动层：`app/bootstrap/` 负责全局初始化、依赖装配、权限前置能力准备

### 备选方案

- 方案 A：更重的经典 Clean Architecture + 每个用例单独 interactor
- 方案 B：更轻的 page-first / service-first 结构

### 取舍理由

- 不选更重的 Clean Architecture：当前产品需要快速验证闭环，过细用例层会提高样板成本。
- 不选 page-first：睡眠记录、提醒、订阅、同步都涉及跨页面共享规则，page-first 很容易把插件调用与业务状态搅在一起。
- 选择 DDD-lite：足够支撑后续多模块拆分，同时控制实现复杂度。

### 架构连接关系

- Flutter 客户端是核心闭环执行端
- Supabase 作为首期账户、云同步、服务端业务快照与边缘逻辑承载
- 系统健康数据、本地通知、小组件、时区能力全部通过数据层 adapter 进入内部模型
- 埋点、日志、崩溃监控作为横切能力接入 `app/bootstrap` 与 `core/observability`

## 5. Flutter 客户端详细技术方案

### 5.1 工程结构

### 推荐方案

使用按 feature 组织的目录结构：

```text
lib/
  app/
    bootstrap/
    router/
    theme/
    entry/
  core/
    error/
    result/
    storage/
    observability/
    time/
    permissions/
  features/
    app_shell/
    onboarding_activation/
    sleep_data_core/
    today/
    bedtime/
    calendar/
    insights/
    profile_settings/
```

每个 feature 内部默认拆为：

```text
domain/
data/
application/
presentation/
```

### 备选方案

- `lib/src/...` 纯技术分层结构
- 全局 `controllers/services/widgets` 结构

### 取舍理由

- 当前产品天生是多闭环 feature 协作，按 feature 分层更适合后续模块拆分与责任边界控制。

### 5.2 状态管理与依赖组织

### 推荐方案

采用 `hooks_riverpod + riverpod_annotation + riverpod_generator` 作为唯一应用级状态管理方案。

### 备选方案

- `flutter_bloc`
- `provider`

### 取舍理由

- 当前仓库已经声明 `flutter_riverpod` / `hooks_riverpod` / `riverpod_annotation`
- 项目规则明确要求显示层默认使用 Hook 方案
- Riverpod 更适合“本地状态 + 异步状态 + 插件状态 + 路由守卫状态”混合产品

### 5.3 路由与守卫

### 推荐方案

使用 `go_router` 统一导航，并通过 provider 驱动路由守卫：

- 首发默认不阻断匿名进入主链路
- 登录态只影响云同步、订阅恢复、跨设备恢复等增强路径
- 睡前模式支持通知 deep link 与首页快捷进入

### 备选方案

- `auto_route`
- 原生 `Navigator 2.0` 手写

### 取舍理由

- `go_router` 与 Riverpod 配合更轻，适合当前节奏
- 不建议在本阶段为了 typed route 引入更重的生成式路由栈

### 5.4 网络与远端访问

### 推荐方案

远端访问分两层：

- BaaS / auth / sync 类能力优先通过 `supabase_flutter` adapter 承接
- 业务 API、Edge Function、自定义远端服务统一通过 `dio + retrofit` 封装

### 备选方案

- 纯 `supabase_flutter`，不引入 `dio`
- 纯 REST 客户端，不使用 Supabase 能力

### 取舍理由

- 纯 Supabase 客户端短期快，但后续边缘逻辑、第三方接口和迁移弹性较弱
- 纯 REST 自建后端成本高，不适合当前首发验证期
- 混合方案让“身份 / 同步 / 远端业务”职责清晰，可保留演进弹性

### 5.5 模型、序列化与错误建模

### 推荐方案

- 领域模型、状态模型、DTO 统一使用 `freezed` + `json_serializable`
- 领域失败类型使用 `freezed` 密封类表达
- 暂不强制引入 `fpdart`，先保持“显式失败模型 + 边界异常映射”

### 备选方案

- 纯手写类 + `equatable`
- 直接异常驱动，无统一失败模型
- `fpdart` 全链路 `Either`

### 取舍理由

- 当前复杂度已足够需要生成式模型，但还不需要把团队认知成本抬到全函数式错误流

### 5.6 本地数据与缓存

### 推荐方案

- `drift`：睡眠记录、标签、恢复计划、周报快照、同步任务队列
- `flutter_secure_storage`：会话令牌、匿名绑定令牌、敏感标识
- `shared_preferences`：轻量配置、首次引导状态、提醒开关、小组件偏好

### 备选方案

- `isar` 作为主数据库
- 全部落 `shared_preferences`

### 取舍理由

- 当前产品存在时间序列、统计汇总、同步队列与条件查询，`drift` 更合适
- 不应把业务主数据降级成 key-value 伪数据库

### 5.7 登录、会话与匿名升级

### 推荐方案

- 首发支持匿名本地使用
- 后续通过 Supabase Auth 进行账号绑定与跨设备同步
- `google_sign_in` / `sign_in_with_apple` 作为平台登录入口，通过统一 auth gateway 转为内部身份状态

### 备选方案

- 首发必须登录
- Firebase Auth + Supabase 数据

### 取舍理由

- PRD 当前默认是“先闭环、后登录”
- 强制登录会直接打击激活
- 双 auth 体系会显著增加会话边界复杂度

### 5.8 插件与平台能力接入策略

### 推荐方案

- `health`：通过 `SleepHealthDataSource` adapter 统一健康数据读取与映射
- `flutter_local_notifications` + `timezone` + `flutter_timezone`：统一本地提醒调度
- `home_widget`：桌面小组件桥接层
- `connectivity_plus` / `device_info_plus` / `package_info_plus`：统一放在 `core/platform`

### 备选方案

- 页面直接调用插件

### 取舍理由

- 当前项目规则明确要求三方包只能通过边界层统一适配
- 插件直连页面会让权限、初始化、降级和测试迅速失控

### 5.9 订阅与权益

### 推荐方案

- `purchases_flutter` 作为订阅购买与恢复购买入口
- 客户端只负责展示权益状态与购买流程
- 服务端 / 云端保留会员快照与关键权益状态，用于多设备一致性

### 备选方案

- 仅客户端本地判断权益
- 直接自建支付订阅体系

### 取舍理由

- 纯本地权益判断在多设备、恢复购买和退款链路上脆弱
- 自建支付不适合当前移动端首发

### 5.10 国际化、主题、配置与权限

### 推荐方案

- 国际化：`flutter_localizations + intl + gen_l10n`
- 主题：在 `app/theme` 建立 token 层，后续承接 `DESIGN.md`
- 权限：在 `core/permissions` 统一定义健康、通知、小组件相关状态机
- 配置：将环境变量、服务端地址、feature flags 放入 `app/bootstrap/config`

### 备选方案

- 页面直接读取配置和权限状态

### 取舍理由

- 当前产品权限路径复杂，必须统一建模，否则设计与实现会频繁错位

### 5.11 错误处理与降级策略

### 推荐方案

- 边界层统一将插件异常、网络异常、鉴权异常映射成内部失败类型
- 展示层只消费可展示状态，不直读底层错误码
- 关键策略是“不断主链路”：授权失败、弱网、同步失败都要保留本地闭环

### 备选方案

- 异常上抛到页面逐个判断

### 取舍理由

- 当前产品有大量“允许失败但不能中断”的场景，必须统一失败语义

## 6. 第三方包选型与最佳搭档

### 能力域：状态管理与依赖组织
推荐主方案：`hooks_riverpod + flutter_riverpod + riverpod_annotation + riverpod_generator`
推荐理由：与项目规则、显示层 Hook 约束和异步状态需求完全一致。
最佳搭档：`go_router`、仓储接口、生成式 provider
备选方案：`flutter_bloc`
避免混搭：不要把 `get_it` 或手写单例再作为第二套全局状态系统
接入注意事项：全部 provider 走 `@riverpod` 生成式写法
升级/维护风险：生成文件需要 CI 校验，避免 stale code

### 能力域：路由与页面守卫
推荐主方案：`go_router`
推荐理由：适合匿名 / 登录混合链路、深链与壳层导航。
最佳搭档：`hooks_riverpod`
备选方案：`auto_route`
避免混搭：不要并存多个 router
接入注意事项：把匿名可用与同步增强的路由守卫拆开
升级/维护风险：壳层和 redirect 规则必须只有一个真相源

### 能力域：数据模型与序列化
推荐主方案：`freezed + freezed_annotation + json_annotation + json_serializable + build_runner`
推荐理由：支持不可变模型、union 状态和稳定 DTO 映射。
最佳搭档：`retrofit`、仓储模式、Riverpod AsyncValue
备选方案：手写 DTO + `equatable`
避免混搭：不要在不同 feature 里混用手写模型和生成式模型
接入注意事项：领域实体与数据 DTO 都保持不可变
升级/维护风险：生成链路必须纳入常规脚本和测试

### 能力域：本地数据库与安全存储
推荐主方案：`drift + flutter_secure_storage + shared_preferences`
推荐理由：满足结构化业务数据、敏感凭据、轻量配置三层分工。
最佳搭档：`sqlite3_flutter_libs`、`path_provider`
备选方案：`isar + flutter_secure_storage`
避免混搭：不要引入第二套主数据库
接入注意事项：同步队列与业务主表分层设计
升级/维护风险：表结构迁移需要在后续模块设计阶段提前规划

### 能力域：健康数据与设备环境
推荐主方案：`health + connectivity_plus + device_info_plus`
推荐理由：覆盖健康读取、联网状态感知与设备诊断需要。
最佳搭档：权限状态机、本地补录兜底流程
备选方案：自建 platform channel
避免混搭：不要同时维护重复的健康数据桥接层
接入注意事项：健康数据读取必须有来源标识和可信状态
升级/维护风险：系统权限差异和平台行为需要真机验证

### 能力域：提醒、时区与小组件
推荐主方案：`flutter_local_notifications + timezone + flutter_timezone + home_widget`
推荐理由：能覆盖睡前提醒、周报提醒、时区调度和桌面快捷入口。
最佳搭档：`shared_preferences` 偏好配置、`package_info_plus`
备选方案：仅本地通知，不做小组件
避免混搭：不要让不同页面各自管理调度逻辑
接入注意事项：提醒时间计算统一走时区基准
升级/维护风险：跨时区、夏令时和平台限制是核心验证点

### 能力域：账号、同步与会员
推荐主方案：`supabase_flutter + google_sign_in + sign_in_with_apple + purchases_flutter`
推荐理由：覆盖登录、云同步、订阅与换机恢复的首期需求。
最佳搭档：安全存储、统一 auth gateway、远端快照表
备选方案：Firebase Auth + RevenueCat + 自建后端
避免混搭：不要并行维护两套会话真相源
接入注意事项：匿名转登录的账号合并策略必须在后端契约里提前约定
升级/维护风险：会员快照、退款状态和多设备一致性要尽早联调

### 能力域：图表、国际化与日志
推荐主方案：`fl_chart + flutter_localizations + intl + logger`
推荐理由：满足趋势展示、国际化和本地结构化日志需要。
最佳搭档：`gen_l10n`
备选方案：后续引入 `sentry_flutter` 或 `firebase_crashlytics` 做生产诊断
避免混搭：不要把日志 SDK、崩溃 SDK、埋点 SDK 做成无边界直连
接入注意事项：生产日志必须脱敏
升级/维护风险：如果不补生产监控，公测后定位问题成本会快速上升

### 默认基础栈结论

本项目推荐“沿用并收束当前仓库已声明的基础栈”，不再重新引入第二套状态、路由、数据库或认证体系。

## 7. 后端协作与接口契约要求

### 推荐方案

首期采用 “`Supabase Auth + Supabase Database/Storage + Edge Function + Flutter 本地优先`” 协作模式。

后端应至少明确这些契约：

- 鉴权模型：匿名本地用户、已绑定账号用户、订阅用户三类状态
- 时间规则：所有云端时间戳使用 `UTC ISO8601`，客户端展示按本地时区转换
- 主键规则：客户端生成稳定 UUID，云端 upsert 以业务主键 + `updated_at` 为准
- 冲突策略：补录 / 标签 / 恢复计划等可编辑数据采用“最后写入生效 + 保留变更时间”
- 订阅契约：客户端购买结果与云端权益快照需可重建、可重放
- 同步契约：支持重试、幂等和弱网恢复，不要求实时双向协作

### 备选方案

- 纯本地首发，后端全部后置
- 纯 REST 自建服务首发

### 取舍理由

- 纯本地首发可以更快，但账号同步与订阅多设备一致性会变成后续大迁移
- 自建服务首发成本过高
- Supabase 适合作为早期统一后端底座，同时保留后续迁移或混合部署空间

### 额外协作要求

- 错误响应统一结构：`code`、`message`、`details`、`trace_id`
- 分页规则：历史记录与报告查询统一使用 cursor 分页，而不是 offset
- 上传下载：如后续引入报告导出或图片资源，同样通过统一 gateway 层承接
- 实时边界：当前产品不把 WebSocket 作为首发必要能力，优先本地通知与拉取同步

## 8. 数据与安全方案

### 推荐方案

- 健康原始数据最小化上云：首发优先只同步业务所需记录、标签、恢复状态与报告快照
- 会话、匿名绑定、敏感标识只进 `flutter_secure_storage`
- 用户偏好、引导状态、小组件配置走 `shared_preferences`
- 结构化业务数据、同步队列、时间序列记录走 `drift`
- 本地日志与远端监控全部做脱敏，禁止输出健康原始敏感字段

### 备选方案

- 全量健康数据上云统一计算
- 全部只放本地，不做任何云端快照

### 取舍理由

- 全量上云会快速放大隐私与合规压力
- 完全不做云端快照会削弱多设备恢复和订阅一致性
- 当前最佳平衡点是“本地为主、云端只存必要业务镜像”

### 安全边界

- 最小权限原则：健康、通知、小组件权限都不应打断主闭环
- Token 生命周期：统一由 auth gateway 与 transport interceptor 管理
- 数据删除与导出：后端与本地都要有可执行路径
- 风险控制：购买、恢复购买、账号合并、同步冲突要保留审计字段

## 9. 埋点、监控与运营支持

### 推荐方案

首期埋点按“页面曝光 + 关键动作 + 漏斗转化 + 权益触点”四层设计：

- 激活漏斗：`app_open`、`onboarding_started`、`goal_setup_completed`
- 行为闭环：`bedtime_mode_entered`、`bedtime_status_selected`、`delay_tag_added`
- 商业化：`paywall_viewed`、`trial_started`、`subscription_purchased`
- 同步与稳定性：`health_permission_granted`、`sleep_record_synced`、同步失败事件

### 备选方案

- 首期只保留最小漏斗埋点，不接崩溃监控

### 取舍理由

- 当前产品强依赖闭环转化与提醒路径，若没有事件分层，很难判断价值断点

### 监控与运营建议

- 本地日志：`logger` 包装统一日志门面
- 生产诊断：公测前补一套崩溃 / 性能监控，优先 `sentry_flutter`，备选 `firebase_crashlytics`
- 远程配置：如果需要价格实验、提醒节奏实验、付费墙策略切换，应在公测前补充 remote config
- 灰度开关：订阅承接、同步策略、运营文案最好具备 kill switch 或配置开关

## 10. 测试与质量保障

### 推荐方案

- 单元测试：时间计算、稳定度规则、恢复建议规则、权限状态机、同步冲突处理
- Drift 测试：记录写入、修正、查询、迁移
- Widget 测试：今日页、睡前页、洞察页关键状态渲染
- 集成测试：首启激活、匿名路径、手动补录、睡前提醒链路、账号绑定恢复
- 契约测试：Supabase auth / sync / entitlement 快照的联调检查

### 备选方案

- 只做集成测试和人工回归

### 取舍理由

- 当前产品在时间、权限、同步、通知这几条线上都非常容易出现“少量条件下才暴露”的错误，必须分层测试

### 重点回归清单

- 健康授权拒绝后仍能完整完成主闭环
- 时区切换后提醒与热力图不误判
- 手动修正不覆盖原始来源标识
- 匿名升级登录后记录不丢失
- 恢复购买、退款、跨设备同步状态正确

## 11. 实施计划与里程碑

### 推荐方案

#### 里程碑 1：项目 bootstrap 与公共底座

- 建立 `lib/` 目录骨架
- 接入 Riverpod、路由、主题、l10n、错误与日志基础
- 建立本地数据库与安全存储基础设施

#### 里程碑 2：本地首发闭环

- 完成目标作息、手动补录、今日页、睡前页、基础周报
- 完成健康数据 adapter 与本地通知调度
- 确保匿名路径可完整使用

#### 里程碑 3：趋势与洞察扩展

- 完成热力图、原因标签、恢复建议、洞察摘要
- 完善数据来源标识、异常态和弱网降级

#### 里程碑 4：账号同步与订阅

- 接入 Supabase Auth、云同步、购买与恢复购买
- 建立权益快照与同步冲突策略

#### 里程碑 5：公测前运营与稳定性

- 完成埋点、崩溃监控、必要 remote config
- 完成回归测试矩阵与真机验证

### 并行流

- 可以并行：本地数据层基础、设计方向确认前的公共代码 bootstrap、后端契约草案
- 阻塞项：登录承接方式、订阅权益快照规则、设计设备预设、最终视觉方向

## 12. 风险清单与替代方案

### 技术风险

- 健康数据平台差异大，真机行为可能与文档不一致
- 通知时区与夏令时处理错误会直接破坏核心闭环
- 匿名转登录的数据合并如果设计过晚，后续迁移成本很高

### 协作风险

- 订阅权益如果没有服务端快照，客户端与商店状态容易不一致
- 设计冻结前如果路由与壳层不明确，后续模块拆分会反复返工

### 发布风险

- 没有崩溃监控与配置开关会降低公测可控性
- 首发范围若把轮班、复杂时差策略强行并入，会显著拖慢闭环验证

### 替代方案

- 如果后端资源不足：允许“本地首发 + 云同步后置”，但必须接受后续迁移成本上升
- 如果订阅暂时不接：保留 paywall 入口与权益占位，延后真实购买链路
- 如果 Google / Apple 账号绑定复杂度过高：首发仅开放匿名 + Apple 登录，其余后置

## 13. 最终结论

### 推荐主方案

Rhythm 应采用“`本地优先 + Feature DDD-lite + Riverpod + GoRouter + Drift + Supabase 增强同步`”作为全局技术基线。

这个方案最符合当前 PRD 的四个核心要求：

- 首发闭环必须离线可用、弱网可降级
- 健康数据、通知、时区、小组件都需要明确插件边界
- 免费层先验证价值，订阅与同步作为增强能力接入
- 后续仍要保留扩展到 Android、模块拆分、设计冻结和订阅增长的空间

### 不推荐路径

- 不推荐首发直接走重型纯 Clean Architecture
- 不推荐页面直连插件与存储
- 不推荐强制登录首用
- 不推荐把后端完全后置到所有客户端功能完成之后

### 进入下阶段前最需要确认的 5 件事

1. 设计设备预设与基础分辨率
2. 登录承接最终策略
3. 订阅权益是否要求后端快照
4. 是否首发就接 remote config / 灰度能力
5. 公测前采用哪套崩溃监控方案

### Handoff Notes For Module Splitting

后续 `flutter-rd-module-splitter` 必须继承这些全局决策：

- 路由唯一真相源是 `go_router`
- 状态管理唯一真相源是生成式 Riverpod
- 本地业务主存储是 `drift`
- 敏感凭据只进 `flutter_secure_storage`
- 账号 / 同步 / 订阅以 Supabase + purchases 组合为主
- 匿名本地闭环优先级高于登录强化
- 所有插件能力必须通过 data adapter 进入内部模型
- 模块拆分只允许在上述公共基线之上展开，不得重新引入第二套路由、状态、数据库或认证体系
