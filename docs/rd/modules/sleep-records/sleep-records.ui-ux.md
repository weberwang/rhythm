# Sleep Records UI/UX RD

## 模块冻结定位

- 模块定位：`Sleep Records` 是 Rhythm 的记录可信度中心，负责承接自动同步、手动补录、结果修正与晚睡原因标注。
- 冻结状态：`frozen_for_architecture`
- 设计源继承：
  - 强制继承 [docs/rd/global-design-guidelines.md](D:/Projects/Flutter/rhythm/docs/rd/global-design-guidelines.md) 的 `product_personality`、`information_hierarchy_principles`、`component_system_principles`、`state_and_feedback_principles`、`engineering_guardrails`。
  - 强制继承 [docs/rd/light-theme-freeze.yaml](D:/Projects/Flutter/rhythm/docs/rd/light-theme-freeze.yaml) 与 [docs/rd/dark-theme-freeze.yaml](D:/Projects/Flutter/rhythm/docs/rd/dark-theme-freeze.yaml) 的输入框、按钮、卡片和状态语义。
  - 本模块必须保持 `warm calm`、克制、细边框卡片、非 dashboard 的全局冻结方向，即使它承载的是“数据修正”任务，也不能退化成管理后台或系统设置页。

## 模块目标与目标用户

- 模块目标：让用户相信“记录是可信的、缺失是可恢复的、修正是被清楚标记的”。
- 目标用户：
  - 自动同步正常的用户
  - 权限拒绝或同步失败的用户
  - 记录缺失或只有部分数据的用户
  - 需要手动修正昨晚结果的用户

## 页面范围与导航入口

- 页面范围：睡眠记录中心页、手动补录页、记录修正页、来源说明区、标签选择弹层、自定义标签输入。
- 导航入口：
  - 今日页快捷入口
  - 日历单日详情入口
  - 我的页数据入口

## 平台基线

- 平台基线：`ios_hig`
- 平台说明：
  - 表单输入、滚轮选择、底部弹层、行内校验、删除确认遵循 iOS 交互基线。
  - 修正和删除类风险操作必须进入确认层，不允许在主列表页直接破坏性提交。
  - 视觉表达仍然服从全局冻结的轻卡片和宽留白，不采用数据库列表或表格式布局。

## 商业目标

- 主要商业目标：提升记录可信度与补录完成率，避免因为一两次数据异常就流失用户。
- 次级商业目标：通过更完整、更可信的记录，为后续洞察与会员价值建立数据基础。
- 商业成功信号：
  - 用户在同步异常时仍能完成补录。
  - 用户理解原始来源和修正记录的边界，不怀疑产品“静默改数据”。

## 艺术指导

- 产品姿态：`precision tool`
- 信息密度：`balanced`
- 视觉温度：`warm calm`
- 视觉语气：可信、审慎、低焦虑、非运维后台
- 页面记忆点：`记录结果主卡 + 来源可信解释 + 轻量修正/补录动作` 的连续关系，而不是长表单或多列表堆叠。
- 风格限制：
  - 不得做成数据库行列表或医学监测报表。
  - 不得用大面积红色强调“缺失”“失败”“延迟”。
  - 不得把原因标签升级成复杂问卷。

## 信息层级

- 一级信息：
  - 当前记录结果
  - 入睡 / 起床时间
  - 相对目标偏移
- 二级信息：
  - 数据来源
  - 可信度状态
  - 补录 / 修正主动作
- 三级信息：
  - 晚睡原因标签
  - 同步说明
  - 部分数据解释
- 四级信息：
  - 深层来源说明
  - 额外管理入口
- 固定阅读顺序：
  1. 当前结果
  2. 来源与可信状态
  3. 当前可执行修正动作
  4. 原因补充与解释

## 核心用户路径

1. 用户看到自动同步结果或缺失提示。
2. 用户理解这条记录来自哪里、是否完整、是否已被修正。
3. 用户必要时执行手动补录或修正。
4. 用户为明显晚睡结果补一个轻量原因标签。
5. 用户回到今日页、日历页或洞察页继续阅读。

## 状态矩阵

| 状态 | 表现要求 |
| --- | --- |
| 理想 | 自动记录清晰显示时间、来源、可信度和偏移，不需要额外解释就能读懂 |
| 空态 | 无任何记录时先给手动补录路径，不把用户放在“失败状态”里 |
| 加载 | 同步中展示等待语义与上次可用数据，不伪装成已完成 |
| 错误 | 同步失败、保存失败、标签保存失败都必须有页内重试和兜底说明 |
| 权限 | 无健康权限时先讲价值，再给手动记录替代路径 |
| 部分数据 | 只有入睡或只有起床数据时，必须明确说明“不完整但仍可保存/修正” |
| 禁用 | 平台能力缺失时说明边界，但不阻断基础记录查看 |
| 成功 | 修正成功后必须保留“已修正”标记和原始来源痕迹 |
| 锁定/会员 | 基础记录查看、补录、修正、标签都不得作为会员能力锁定 |

## 模块级组件冻结骨架

- `record_result_summary_card`
  - 用途：承载当前记录结果、时间区间和相对目标偏移。
  - 状态：`default`、`partial_data`、`corrected`、`empty`。
  - 冻结约束：结果、来源和偏移必须保持同一阅读组，不得被拆成分离面板。
- `source_trust_badge_row`
  - 用途：承载原始来源、修正来源和可信度状态点。
  - 状态：`default`、`warning`、`error`、`disabled`。
  - 冻结约束：来源标记只能做轻量解释，不得膨胀成技术型诊断清单。
- `manual_record_form_sheet`
  - 用途：承载手动补录与修正表单。
  - 状态：`default`、`editing`、`saving`、`save_error`。
  - 冻结约束：字段数量维持最小闭环，禁止让标签或高级字段压过时间输入主任务。
- `late_reason_chip_group`
  - 用途：承载晚睡原因标签选择与补充说明。
  - 状态：`default`、`selected`、`multi_selected`、`custom_input`。
  - 冻结约束：标签是轻量补充动作，不得升级成长问卷或必填流程。

## 设计源与模块继承合同

- Pencil 来源：当前冻结先以全局设计源为准；后续如果引入 Pencil 页面，必须验证其是否保留来源可信度层级、补录动作节奏和非后台化视觉基调。
- 全局继承重点：
  - 继承“统计数字应与解释文案共生”的原则，因此时间、偏移、来源必须共同出现。
  - 继承“权限、同步、数据缺失是一等状态”的原则，因此无权限、失败、部分数据都必须有独立版式。
  - 继承“页面骨架以竖向单列为主”的原则，不使用复杂表格或双栏面板。
- 主题继承重点：
  - 输入框、标签选择器、按钮、轻卡片必须直接映射主题冻结文件的语义角色。
  - Dark 主题下来源说明卡与错误说明卡仍需边界清晰，不允许融成一整片深底。

## 设计冻结卡

- 当前状态：`frozen_for_architecture`
- 必须一致项：
  - 原始来源、修正来源、可信度必须分层表达，不能混成一段模糊状态文案。
  - 当前记录结果必须先于补录/修正表单出现，先帮助用户理解现状，再进入编辑。
  - 补录和修正动作必须低步骤、低焦虑，默认以最少字段完成闭环。
  - 原因标签入口必须保持轻量点选，不升级为长问卷或必填深表单。
  - 同步失败时必须明确“当前数据是否丢失”和“现在还能做什么”。
- 允许工程化调整项：
  - 来源解释可以做成卡片内说明、展开区或底部弹层，但不能变成低发现路径。
  - 时间输入可以用原生 picker 或项目统一选择器，只要保持轻节奏和可读性。
  - 标签展示可以用 chip、列表或底部表单，但默认交互步数不能增长。
- 平台不可偏离项：
  - 修正、删除、覆盖类操作必须进入确认层。
  - 表单输入区、确认按钮、取消路径必须满足平台触控尺寸与可预期返回逻辑。
  - 不允许在编辑中途通过系统 toast 代替关键结果确认。
- Prompt 约束：
  - 禁止做成数据库表格界面、后台管理页或系统设置串联页。
  - 禁止使用大面积告警红描述缺失、延迟、无权限。
  - 禁止把来源说明藏进低发现帮助链接。
  - 禁止要求用户先完成标签再允许保存记录。

## 视觉系统锚点

- 记录结果主卡：
  - 时间与偏移是主视觉信息，允许更强字号层级，但仍保持轻重量和大留白。
  - 卡面基调以 `surface`、细边框、轻强调色为主，不使用强色块压迫。
- 来源可信说明：
  - 以次级卡片或卡内分区承载，强调“可解释”而不是“技术详情密度”。
  - 来源标签、修正标记和状态点应使用统一轻量状态语言。
- 补录/修正表单：
  - 使用轻表单节奏，字段分组清晰，不做长设置页。
  - 危险操作只能在独立确认层出现，视觉上显著晚于主保存动作。
- 模块级视觉约束：
  - 单屏最多一个高强调结果面，其余说明必须降级。
  - 缺失和失败说明使用暖中性色卡片，不采用警报横幅主导首屏。
  - 标签区只能是轻量补充，不得变成与记录结果同权重的大版块。

## 商业化触点

- 本模块基础能力不商业化：
  - 记录查看
  - 手动补录
  - 基础修正
  - 原因标签
- 可关联商业价值的触点只允许作为次级承接：
  - 更深历史记录解释
  - 更丰富的长期原因聚合
  - 洞察页中的高级恢复建议
- 商业化规则：
  - 不在记录修复流程中插入付费阻塞。
  - 任何会员价值必须建立在“先把记录修好”的基础上。

## UI/UX 与实现交接验收

- 用户必须能清楚区分：
  - 原始来源
  - 修正来源
  - 当前最终显示结果
- 手动补录流程必须在疲劳状态下也能快速完成，不得要求多屏深跳。
- 缺失、延迟、部分数据三类状态必须独立可读，不能共用同一警示块。
- 同步失败时，用户必须同时读懂“数据有没有丢”和“现在还能做什么”。
- 若未来 Pencil 方案不能承载上述来源可信层级与轻补录路径，必须回到冻结评审，而不是实现侧自行裁切。
