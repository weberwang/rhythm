## 1. PRD 需求理解

### 产品目标

- Rhythm 不是医学睡眠产品，而是本地优先的作息行为管理 App。
- 核心价值是帮助用户完成“今晚少拖延一点、次日知道为什么、接下来几天回到节奏”的闭环。
- 商业闭环围绕免费层结果反馈与付费层持续改善能力展开。

### 目标用户

- 核心用户是 20-35 岁长期晚睡但有调整意愿的人群。
- 高价值细分包括远程办公、城市白领、跨时区用户与轮班用户。
- 产品需兼顾疲劳状态下的低负担输入、数据不完美时的可修正体验与高意图转化触点。

### 主场景

- 首次激活：登录/匿名、健康授权或手动路径、目标作息设置、提醒策略、小组件引导。
- 日常闭环：睡前进入、次日反馈、标签补录、恢复建议、周复盘。
- 商业触点：恢复计划、稳定度解释、长期历史、月报、高级目标策略。

### 范围内功能

- 健康数据读取与手动补录
- 目标作息与提醒设置
- 今日页、日历页、睡前页、洞察页、我的页
- 会员、账号同步、小组件、通知

### 明确不做

- 医学诊断
- 社区打卡
- 硬件联动
- 首发 AI 聊天教练

## 2. 假设前提与待确认项

### 假设前提

- 首发默认支持匿名本地使用，并允许后续绑定账号与云同步。
- 首发后端以 Supabase 为账号与同步基础设施，避免额外引入自建 API 网关。
- 会员体系通过 `purchases_flutter` + StoreKit / Google Play 订阅承接，不在首发引入自建账单系统。
- 本地闭环优先于云端一致性；网络不可用时仍需保证本地记录、提醒与查看。
- Android 与 iOS 同步遵循相同业务模型，但平台授权、通知与健康读取在适配层分流。

### 待确认项

- 首发是否把匿名模式作为一等路径长期保留。
- 海外区与中国区是否同一套定价文案与付费页结构。
- 轮班/时差策略是首发付费能力还是 V1.0 后置能力。
- 事件埋点是优先走 Supabase 事件表，还是后续补接专门分析 SDK。
- 会员权益是否需要服务器侧二次校验与缓存窗口控制。

## 3. 业务流程与页面范围

### 主业务闭环

1. 用户完成首次激活与目标作息设置。
2. 夜间收到提醒，从通知/小组件/今日页进入睡前模式。
3. 次日查看昨晚结果，补录原因标签，获得恢复建议。
4. 周期性查看周报、稳定度与历史趋势，并在高意图场景触发付费。

### 关键异常流

- 健康权限未授权或有授权但无数据。
- 网络不可用或同步失败。
- 用户仅手动补录、不登录、跨时区、轮班、恢复计划锁定、历史数据锁定。

### 粗粒度页面范围

- 启动与根壳
- 引导漏斗
- 今日首页
- 睡前模式
- 日历与单日详情
- 洞察与周报
- 我的与设置

## 4. 总体技术架构

### 推荐方案

- 采用 `DDD by feature + local-first + optional cloud sync` 的总体结构。
- 根目录按 `lib/app`、`lib/core`、`lib/features` 划分。
- 业务模块按功能边界拆分，领域模型、应用编排、数据适配、显示层分别归位。
- 本地数据库以 `drift` 为结构化数据主存，云同步与账号体系通过 `supabase_flutter` 适配。
- 健康读取、通知、小组件、购买、登录等能力统一下沉到数据/基础设施边界，不允许页面直接调用三方包。

### 备选方案

- `service + page` 轻量目录结构：初期上手快，但会把健康权限、同步、恢复计划、订阅判断混杂进页面或 controller。
- `REST API first + remote source of truth`：适合强联网产品，但会牺牲本地优先体验，且会放大授权失败、离线与同步冲突复杂度。

### 取舍理由

- Rhythm 的首要矛盾不是复杂远端业务，而是“弱网/无网仍要可用、数据源不稳定仍要闭环、行为反馈要连贯”。
- local-first 能最小化云端依赖，对健康数据延迟与人工修正更友好。
- DDD by feature 能避免 `今日/睡前/洞察/我的` 交叉污染，适合后续逐模块并行推进。

## 5. Flutter 客户端详细技术方案

### 5.1 项目结构

### 推荐方案

- `lib/app/`: bootstrap、router、全局 provider scope、环境配置、主题装配
- `lib/core/`: 日志、错误映射、时间/时区工具、通用适配、基础 UI token 映射
- `lib/features/<module>/`: `domain` / `application` / `data` / `presentation`
- `lib/l10n/`: ARB 国际化资源

### 备选方案

- 按页面或按技术层统一堆叠所有代码

### 取舍理由

- 当前 PRD 明确存在多用户旅程、多状态矩阵与多插件能力；若不按 feature 边界拆，后续演进会很快失控。

### 5.2 状态管理与依赖注入

### 推荐方案

- `hooks_riverpod` + `riverpod_annotation` 为唯一状态组织入口。
- 页面级状态、局部表单状态、生命周期副作用均落在 Hook 路径。
- 长期稳定 Provider 必须通过注解生成，避免手写旧风格 Provider 与新风格混用。

### 备选方案

- 纯手写 Riverpod Provider
- `Bloc/Cubit`

### 取舍理由

- 当前依赖栈已明确押注 Riverpod 3 + Hook 方案；继续统一可减少样板代码并保持后续生成链路一致。

### 5.3 路由与守卫

### 推荐方案

- `go_router` 统一管理根壳、引导态、主壳、订阅受限入口与深链分发。
- 通过根 redirect 判断：
  - 首次使用是否完成 onboarding
  - 是否已配置目标作息
  - 是否需要显示权限修复页
  - 是否从通知/小组件/深链跳转到指定页面

### 备选方案

- 页面内 if/else 跳转
- 并行导航状态机

### 取舍理由

- Rhythm 存在多入口启动、首次引导与正式主壳切换、通知唤起睡前模式等场景，必须由 root shell 统一裁决。

### 5.4 数据模型与序列化

### 推荐方案

- 领域模型与 DTO 统一使用 `freezed` / `json_annotation`。
- `GoalSchedule`、`SleepRecord`、`BedtimeSession`、`SleepDelayTag`、`RecoveryPlan`、`Report`、`MembershipSnapshot`、`SyncTask` 作为首批核心对象。

### 备选方案

- 手写可变模型与手写 map 转换

### 取舍理由

- 当前 PRD 对状态矩阵、修正状态、同步来源、会员锁定都有明确结构化诉求，生成式模型更稳。

### 5.5 本地存储与云同步

### 推荐方案

- `drift`：结构化业务数据主存
- `flutter_secure_storage`：敏感凭据与匿名绑定信息
- `shared_preferences`：轻量引导标记、布尔开关、非敏感偏好
- `supabase_flutter`：登录、会话恢复、云备份/换机恢复、事件同步

### 备选方案

- 仅用 `shared_preferences`
- 直接以云端为唯一真相

### 取舍理由

- PRD 强调“授权失败仍可闭环”“网络不可用不阻断”，结构化本地数据与同步队列是必须项。

### 5.6 健康、通知、小组件与平台能力

### 推荐方案

- `health`：HealthKit / Health Connect
- `flutter_local_notifications` + `timezone` + `flutter_timezone`：作息提醒、周报提醒
- `home_widget`：桌面小组件入口
- `device_info_plus` / `connectivity_plus`：诊断与连通性提示

### 备选方案

- 首发仅手动记录、无需通知与小组件

### 取舍理由

- 商业 PRD 已把睡前模式进入率和桌面存在感列为关键指标，平台能力不能长期停留在说明文案。

### 5.7 鉴权、会员与会话

### 推荐方案

- `sign_in_with_apple`、`google_sign_in` 作为平台登录入口。
- Supabase 维护用户档案、匿名绑定和同步身份。
- `purchases_flutter` 维护订阅购买、恢复购买与会员态；会员态在本地缓存快照，并在关键入口回源校验。

### 备选方案

- 首发不做账号体系
- 自建支付状态表与收据校验链路

### 取舍理由

- PRD 已经把跨设备同步、会员与付费触点放入 MVP/P1 范围，自建支付体系成本高且上线风险大。

### 5.8 国际化、主题与文案

### 推荐方案

- 使用 `flutter gen-l10n` + `lib/l10n/*.arb`
- 所有用户可见文案从 `app_en.arb` 起步，再同步其他语言资源
- 主题值不在代码中猜测，后续由 `light-theme-freeze.yaml` / `dark-theme-freeze.yaml` 映射

### 备选方案

- 页面中直接写死中文
- 先实现后补国际化

### 取舍理由

- PRD 已明确存在双语区域与商业化场景，不应把国际化当成后补工作。

## 6. 第三方包选型与最佳搭档

### 能力域：状态管理与依赖注入

- 推荐主方案：`hooks_riverpod + riverpod_annotation + riverpod_generator`
- 推荐理由：统一生成 Provider，兼顾 Hook 页面与可测试性
- 最佳搭档：`flutter_hooks`
- 备选方案：手写 Provider
- 避免混搭：不要把注解式 Provider 与老式全手写风格长期并存

### 能力域：导航与启动分发

- 推荐主方案：`go_router`
- 推荐理由：原生支持 redirect、深链、嵌套路由与 root shell
- 最佳搭档：`app-shell` 模块
- 备选方案：手写 Navigator 2.0
- 避免混搭：不要在业务页面里重复维护导航状态机

### 能力域：本地数据与模型

- 推荐主方案：`drift + sqlite3_flutter_libs + freezed + json_annotation`
- 推荐理由：结构化、可查询、适合热力图与周报等聚合场景
- 最佳搭档：`path_provider`, `uuid`, `path`
- 备选方案：纯 JSON 文件
- 避免混搭：不要把核心业务数据长期散落在 `shared_preferences`

### 能力域：账号、同步与会员

- 推荐主方案：`supabase_flutter + sign_in_with_apple + google_sign_in + purchases_flutter`
- 推荐理由：能覆盖同步、身份恢复、会员购买和恢复购买
- 最佳搭档：`flutter_secure_storage`
- 备选方案：匿名本地-only + 后续补账号
- 避免混搭：不要在页面里直接拼装 OAuth、Supabase、RevenueCat 调用

### 能力域：健康与提醒

- 推荐主方案：`health + flutter_local_notifications + timezone + flutter_timezone + home_widget`
- 推荐理由：与产品北极星指标直接相关
- 最佳搭档：`device_info_plus`, `connectivity_plus`
- 备选方案：仅保留手动记录
- 避免混搭：不要把权限弹窗、调度逻辑分散在多个页面

### 能力域：趋势与格式化

- 推荐主方案：`fl_chart + intl`
- 推荐理由：足够覆盖周趋势、热力图周边图示与多语言日期
- 备选方案：纯自绘
- 避免混搭：不要在多个页面重复手写时间格式化与图形占位

## 7. 后端协作与接口契约要求

### 推荐方案

- 首发以 Supabase 作为后端协作中心，不额外引入 REST API 总线。
- 同步对象至少包括：目标作息、手动修正记录、原因标签、恢复计划状态、会员快照、周报摘要、设备绑定信息。
- 时间统一使用 ISO 8601 UTC 存储，展示层基于本地时区转换。
- 同步需具备：
  - `updated_at` 冲突比较
  - 幂等写入键
  - 本地优先的失败重试队列
  - 明确的数据来源字段

### 备选方案

- 自建 REST API + 自建鉴权与同步协议

### 取舍理由

- 当前产品更需要可靠的闭环速度而非大规模自定义后端能力。

## 8. 数据与安全方案

### 推荐方案

- 敏感信息（token、匿名绑定 key、订阅校验快照）存入 `flutter_secure_storage`
- 非敏感布尔配置与引导态存入 `shared_preferences`
- 结构化业务数据存入 `drift`
- 所有自动记录必须保留 `source`, `confidence`, `isManuallyAdjusted` 字段
- 日志中禁止写入原始健康数据与支付凭据

### 备选方案

- 单一存储层承接全部数据

### 取舍理由

- PRD 明确要求“数据可信但可修正”，同时又要求同步与隐私边界清晰，必须按敏感级别分层存储。

## 9. 埋点、监控与运营支持

### 推荐方案

- 先按 PRD 埋点清单建立事件接口与枚举，不直接把埋点散落在页面。
- 本地记录事件并在同步可用时上报到 Supabase 事件表或后续分析服务。
- 建立以下三类可观测性：
  - 激活漏斗
  - 行为闭环
  - 商业化触点

### 备选方案

- 等上线后再补埋点

### 取舍理由

- PRD 的商业假设高度依赖授权率、睡前进入率、转化触点效果，埋点不能后置到功能完成之后。

## 10. 测试与质量保障

- 单元测试：时间偏移算法、稳定度计算、恢复计划触发规则、会员锁定判断
- 仓储/契约测试：健康读取 adapter、同步冲突处理、订阅状态映射
- Widget 测试：onboarding 漏斗、今日页主状态、睡前模式交互、日历无数据态、付费锁定态
- 集成测试：首次激活、手动补录、通知进入睡前页、周报查看主路径
- 发布前检查：`flutter gen-l10n`、`build_runner`、`flutter analyze`、`flutter test`、权限真机验收

## 12. 风险清单与替代方案

- 技术风险：健康数据延迟或平台差异导致“昨晚结果”解释不一致
  - 替代方案：显式可信度与手动修正路径
- 协作风险：产品希望加入更多分析/监控能力，但当前依赖栈尚未确定第三方分析 SDK
  - 替代方案：先抽象事件层，后接具体后端
- 发布风险：订阅、登录、健康权限、小组件涉及多平台真机验证
  - 替代方案：把平台能力验收放到独立清单，不与页面视觉验收混淆
- 范围风险：轮班/时差/匿名/地区策略未定会影响若干模型
  - 替代方案：先冻结接口与扩展位，不在首轮实现中提前复杂化

## 13. 最终结论

- 推荐主路径是：`Flutter DDD by feature + local-first + optional Supabase sync + RevenueCat membership + shared freeze first`。
- 这条路径最符合 Rhythm 的产品本质：先保证本地行为闭环，再逐步叠加云端同步与商业化深度。
- 模块级工作应继承以下不可变全局决策：
  - 状态管理只用 Riverpod 注解链
  - 路由只用 `go_router`
  - 结构化数据只用 `drift`
  - 用户文案必须国际化
  - 页面不得直接依赖三方包实现
