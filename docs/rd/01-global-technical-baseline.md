## 1. PRD 需求理解

### 1.1 产品目标

Rhythm 的目标不是做一个睡眠数据看板，而是做一个本地优先的作息行为管理产品，帮助长期晚睡用户围绕“目标作息 - 睡前进入 - 次日反馈 - 原因标记 - 恢复建议 - 周复盘”形成持续可回访的闭环。

### 1.2 目标用户

- 核心用户：20-35 岁、长期晚睡、愿意调整作息但不希望被强打卡约束的人群。
- 次级用户：跨时区、出差、轮班等节奏不稳定人群，但首发不把复杂策略作为主闭环。

### 1.3 核心场景

- 首次进入后，在 2 分钟内完成可用激活。
- 晚间收到提醒后，以尽量低的操作成本进入睡前模式。
- 次日打开后，快速理解昨晚结果、偏离原因和今天的恢复建议。
- 周期性回看时，以热力图、周报和稳定度解释建立长期价值。
- 在高意图场景里承接订阅，而不是在首开、授权或异常处理中打断用户。

### 1.4 范围内功能

- Onboarding、账号入口、健康数据授权、目标作息设置、提醒设置
- 今日页、睡前模式、睡眠记录、手动补录、原因标签
- 日历热力图、周报洞察、恢复建议
- 小组件、通知、账号同步、会员基础能力

### 1.5 明确不做

- 医疗诊断和疗效承诺
- 社区、陪伴、监督打卡
- 复杂 AI 教练作为首发主链路
- 硬件深度联动和医学评分体系
- 与当前业务迭代混合的大规模目录迁移

## 2. 假设前提与待确认项

### 2.1 假设前提

- 首发仍以移动端行为闭环为核心，桌面/Web 仅作为工程壳存在，不承诺完整能力对齐。
- 首发允许匿名本地使用，再通过账号体系承接跨设备同步与恢复。
- 首发远端能力以 `supabase_flutter` 提供的账号、会话与数据同步为主，不引入独立 REST API 网关。
- 睡眠数据的业务主判断以本地记录和本地规则为准，云端同步是增强能力而不是单点依赖。
- 周报、稳定度和恢复建议首发允许采用规则模型，不依赖首期 AI 服务。
- 会员、登录、同步、通知、健康权限都需要生产级失败态和降级路径。

### 2.2 待确认项

- 中国区与英语区是否首发同步上线；这会影响默认埋点策略、文案校验和支付承接节奏。
- 匿名用户是否允许完整使用会员试用链路；这会影响 Supabase 匿名身份与购买绑定策略。
- 轮班模式与时差模式进入 V1.0 还是延后；这会影响 `GoalSchedule` 结构与时区策略复杂度。
- 是否首发接入远程配置 / AB 实验；这会影响埋点、发布和 kill switch 设计。
- 会员购买是否只覆盖 App Store / Google Play，还是要预留 Web 端权益同步入口。

### 2.3 影响说明

- 若匿名使用被取消，需要重写启动分发和 onboarding 路径的守卫模型。
- 若首发即要求远程实验与灰度，需要在监控与发布章节升级到增长型交付栈。
- 若首发引入轮班 / 时差高级策略，需要在模块拆分阶段提前拆出独立规则域，而不是混进普通目标作息表单。

## 3. 业务流程与页面范围

### 3.1 主业务流程

1. 启动分发：判断首开、登录态、匿名本地状态、必要配置状态。
2. Onboarding：价值说明 -> 登录选择 / 匿名继续 -> 健康数据授权 / 手动路径 -> 目标作息设置 -> 提醒策略 -> 小组件引导 -> 进入首页。
3. 晚间闭环：通知 / 小组件 / 今日页进入睡前模式 -> 记录今晚状态 -> 触发轻量收尾动作。
4. 次日闭环：读取自动或手动睡眠结果 -> 展示偏移和恢复建议 -> 补录原因标签。
5. 周复盘闭环：生成周报摘要 -> 展示稳定度、主要原因、恢复效果 -> 引导调整目标策略。
6. 商业化闭环：在高意图场景展示付费价值 -> 完成订阅 -> 同步权益到多端。

### 3.2 异常流程

- 健康权限拒绝：退化到手动补录，不阻塞进入主链路。
- 健康权限已开但数据为空：进入“等待数据 / 手动记录”状态，不误判为失败。
- 网络不可用：本地功能继续可用，同步与购买展示可恢复提示。
- 账号登录失败：允许保留匿名本地态，不丢当前配置。
- 会员状态拉取失败：保留上次快照与受限能力边界，避免误开权益。
- 时区变化：暂停直接按普通阈值判定，提示用户确认时区语义。

### 3.3 页面范围

- 启动与引导：启动页、欢迎页、登录选择页、权限页、目标设置页、提醒页、小组件引导页、完成过渡页
- 一级主模块：今日、日历、睡前、洞察、我的
- 二级页面：通知设置、目标设置、时区模式、账号同步、数据隐私、会员页、周报详情、手动补录等

### 3.4 导航关系

### 推荐方案

- 顶层使用 `/launch` 进行启动分发。
- 一级模块维持 5 个根路由 tab。
- 设置、详情、表单、说明页统一走二级推进页，而不是混入 tab 层级。

### 备选方案

- 用单页状态机承接启动到首页的所有流程。
- 采用嵌套路由较重的多 navigator 方案承接所有详情页。

### 取舍理由

- 当前产品的主链路明确、一级模块稳定，`GoRouter + /launch + 5 tab` 足够表达，且已与现有代码事实一致。
- 单页状态机会让启动、登录、首开、匿名态和同步态相互耦合，不利于后续模块拆分。
- 更重的嵌套路由方案只有在复杂多栈导航或深链矩阵显著增长时才值得引入。

## 4. 总体技术架构

### 4.1 推荐方案

采用“本地优先 + 明确分层 + feature 边界组织 + 可选云同步增强”的 Flutter 架构。

- 表现层：`hooks_riverpod` 驱动页面、表单、局部状态和副作用。
- 应用层：用例编排、控制器、聚合视图状态。
- 领域层：不可变实体、规则、值对象、仓储接口。
- 数据层：本地数据库、平台插件适配、Supabase 远端同步、购买与登录接入。
- 基础设施：启动装配、路由、主题、本地化、全局配置、分析与日志。

### 4.2 备选方案

- `Bloc/Cubit` 驱动的事件流架构。
- 更传统的 `Provider + Service + Repository` 轻架构。
- 一体化“页面直调插件 / SDK”的快速 MVP 架构。

### 4.3 取舍理由

- 当前产品同时包含健康权限、离线记录、同步、会员、通知、小组件和多状态 UI，复杂度已超过轻量页面直调架构的舒适区。
- `Riverpod + 注解生成 + 分层仓储` 能兼顾可维护性、局部迭代效率和测试隔离。
- `Bloc` 不是不可用，但当前仓库已明确基于 `flutter_riverpod` 与 `hooks_riverpod` 建立工程约束，转向 `Bloc` 只会增加迁移成本。

### 4.4 架构边界

- `lib/app/`：启动装配、主题、路由、全局入口
- `lib/core/`：跨业务技术能力
- `lib/data/`：共享基础设施或跨 feature 数据实现
- `lib/features/<feature>/`：业务主边界
- `lib/shared/`：真正稳定的跨模块 UI 或基础能力

### 4.5 与外部系统关系

- Flutter 客户端：主业务承载
- HealthKit / Health Connect：睡眠数据来源
- Supabase：账号、会话、云同步
- RevenueCat（`purchases_flutter`）：订阅与权益状态
- 本地通知与时区组件：提醒调度
- Home Widget：桌面入口和快照

## 5. Flutter 客户端详细技术方案

### 5.1 项目结构

### 推荐方案

- 维持 `lib/features/*` 为当前正式业务边界。
- 每个 feature 默认分为 `presentation / application / domain / data`。
- 页面状态、表单状态、领域实体统一使用不可变模型和生成代码。

### 备选方案

- 直接推进到 `lib/modules/*` 大迁移。
- 保持“按技术层集中放置”的大目录结构。

### 取舍理由

- 当前仓库已经以 `features/*` 运转，继续在同一边界内演进成本最低。
- 现在推进全仓迁移会把“PRD 落档”和“结构治理”混在一起，风险不成比例。

### 5.2 状态管理与依赖组织

### 推荐方案

- 全面采用 `flutter_riverpod + hooks_riverpod + riverpod_annotation + riverpod_generator`
- 页面默认使用 `HookConsumerWidget` / Hook 方案
- 控制器与 provider 默认用 `@riverpod` 注解生成

### 备选方案

- `flutter_riverpod` 手写 provider，不使用注解生成
- `Bloc/Cubit`

### 取舍理由

- 当前项目已有明确约束和现成生成链路，继续使用注解生成能减少样板和命名漂移。
- 手写 provider 虽然更直观，但在中长期会放大生命周期和命名不一致问题。

### 5.3 路由与守卫

### 推荐方案

- 统一使用 `GoRouter`
- 启动守卫集中在 `/launch`
- 登录态、首开状态、匿名可用状态、必要配置完成状态统一在启动分发层决策

### 备选方案

- `auto_route`
- 业务页内自行判定后跳转

### 取舍理由

- 目前的主难点不在路由代码生成，而在多种启动状态的一致守卫。
- `GoRouter` 已在仓库中使用，继续保持单一路由体系最稳妥。

### 5.4 远端与同步

### 推荐方案

- 近期不引入 `dio + retrofit` 通用网络层
- 远端账号与同步优先基于 `supabase_flutter` 封装 feature 级数据源
- 将同步设计为“本地记录 -> 队列 -> 云端对账”的增强链路

### 备选方案

- 提前建立完整 REST API 基础层
- 所有远端能力直接散落在页面或 controller 中调用 SDK

### 取舍理由

- 当前业务的核心远端诉求是会话、用户绑定和可选云同步，不是复杂独立 API 产品。
- 先用 Supabase 封装边界可以避免预铺一层暂时没有真实需求的通用传输抽象。

### 5.5 本地数据与缓存

### 推荐方案

- `Drift`：睡眠记录、标签、同步队列、周报快照等结构化数据
- `SharedPreferences`：轻量布尔标记、引导完成态、非敏感偏好
- `FlutterSecureStorage`：敏感会话、匿名身份绑定、订阅关联凭据

### 备选方案

- 主要依赖 Key-Value 存储
- 使用对象库替代 `Drift`

### 取舍理由

- 该产品天然存在日期查询、筛选、统计和同步对账需求，关系型本地存储更稳。
- 用 Key-Value 模拟业务数据库会显著放大迁移和查询成本。

### 5.6 模型、序列化与错误处理

### 推荐方案

- 采用默认通用基础栈：`freezed` + `json_annotation` + `json_serializable` + `build_runner`
- 领域失败默认先用 `freezed` 联合类型表达，不强制引入 `fpdart`
- 通过边界层把平台错误、SDK 错误、数据库错误映射为项目内失败模型

### 备选方案

- 手写模型和 `copyWith`
- 全面 exception 驱动
- 引入 `fpdart` 作为默认项目基础

### 取舍理由

- 当前业务复杂度足以支撑模型生成，但还没到必须全面函数式错误流的程度。
- 先把错误边界显式化，比强推 `Either` 更符合当前团队成本与收益平衡。

### 5.7 配置、本地化、主题与权限

### 推荐方案

- 配置：统一通过 `--dart-define` 注入运行时配置
- 本地化：`flutter_localizations + intl + gen_l10n`
- 主题：集中在 `lib/app/theme`，页面只消费 token
- 权限：健康、通知、小组件等插件接入集中在 data / bootstrap 边界，不在页面散落平台判断

### 备选方案

- 多 Flavor 提前铺开
- 页面直接写文案或本地化 Map

### 取舍理由

- 当前产品首要问题是闭环可交付，不是多环境矩阵治理。
- 本地化已经是显性需求，不能以后置“先写死中文”的方式拖延。

### 5.8 性能与可测试性

### 推荐方案

- 通过 feature 边界和仓储抽象降低集成复杂度
- 图表、热力图、周报等 UI 结构优先拆分为独立组件
- 平台插件能力必须有 Fake / Mock 或内存实现支撑测试

### 备选方案

- 页面直接持有 SDK 实例
- 依赖真机手工回归验证

### 取舍理由

- 健康数据、通知和购买都带平台差异，不抽象就无法稳定测试。
- 当前项目后续还会持续迭代，必须从现在就控制可测性债务。

## 6. 第三方包选型与最佳搭档

本项目采用“以现有依赖栈为主、按能力域组织”的方案，不新增一套与现有仓库相冲突的基础设施。

### 6.1 状态管理与依赖组织

- 能力域：状态管理与依赖组织
- 推荐主方案：`flutter_riverpod` + `hooks_riverpod` + `riverpod_annotation` + `riverpod_generator`
- 推荐理由：与当前工程事实一致，适合多 feature、多表单、多启动状态场景
- 最佳搭档：`go_router`、`freezed`
- 备选方案：`Bloc/Cubit`
- 避免混搭：不要在同一 feature 同时引入全局 `Bloc` 状态体系和 Riverpod 主状态体系
- 接入注意事项：所有稳定 provider 默认走注解生成；显示层默认用 Hook 方案
- 升级/维护风险：Riverpod 版本升级需同步生成器与注解版本

### 6.2 路由与页面守卫

- 能力域：路由与页面守卫
- 推荐主方案：`go_router`
- 推荐理由：当前一级模块、启动分发和二级详情足够适配，且已有落地
- 最佳搭档：`flutter_riverpod`
- 备选方案：`auto_route`
- 避免混搭：不要同时维护第二套路由抽象
- 接入注意事项：将守卫集中在 `/launch` 和路由装配层
- 升级/维护风险：深链和多 navigator 复杂度升高时要补 typed wrapper

### 6.3 本地数据、安全存储与同步缓存

- 能力域：本地数据、安全存储与缓存
- 推荐主方案：`drift` + `shared_preferences` + `flutter_secure_storage`
- 推荐理由：与本地优先产品形态完全匹配，职责边界清晰
- 最佳搭档：`path_provider`、`sqlite3_flutter_libs`
- 备选方案：对象型数据库或更多 Key-Value 存储
- 避免混搭：不要再引入第二主数据库；不要把敏感凭据落到 `shared_preferences`
- 接入注意事项：同步队列和业务主记录分表设计；保留来源与修正标记
- 升级/维护风险：数据库 schema 演进需要 migration 策略和回归测试

### 6.4 健康数据与设备能力

- 能力域：健康数据与设备环境
- 推荐主方案：`health`
- 推荐理由：覆盖 HealthKit / Health Connect，适合当前产品最核心的数据来源
- 最佳搭档：本地记录仓储、权限网关、可信度标记模型
- 备选方案：平台原生桥接自研
- 避免混搭：不要在不同页面直接分别调用原生能力
- 接入注意事项：权限失败、数据为空、数据延迟都必须有一等状态
- 升级/维护风险：平台权限策略变化会影响稳定性，需要真机回归

### 6.5 通知、小组件与时区

- 能力域：提醒、小组件与时区
- 推荐主方案：`flutter_local_notifications` + `flutter_timezone` + `timezone` + `home_widget`
- 推荐理由：覆盖调度、系统时区、桌面入口与快照展示
- 最佳搭档：目标作息规则、通知设置仓储、小组件桥接网关
- 备选方案：先做说明页，不接真实提醒
- 避免混搭：不要再引入第二套通知调度主栈
- 接入注意事项：调度必须基于用户目标时间和系统时区，不要硬算本地时间
- 升级/维护风险：各平台调度限制不同，需要平台差异测试

### 6.6 账号、同步与会员

- 能力域：账号、同步与会员
- 推荐主方案：`supabase_flutter` + `google_sign_in` + `sign_in_with_apple` + `purchases_flutter`
- 推荐理由：与当前产品“匿名可进、登录增强、订阅承接、跨端恢复”的商业模型匹配
- 最佳搭档：`flutter_secure_storage`、本地同步队列、会员快照仓储
- 备选方案：后续出现独立账号体系时再引入单独后端鉴权层
- 避免混搭：不要在不同 feature 各自维护登录态与权益状态
- 接入注意事项：购买权益与匿名 / 登录身份绑定策略必须统一设计
- 升级/维护风险：第三方登录和购买依赖平台配置，CI 不能完全替代真机验证

### 6.7 图表与展示层辅助

- 能力域：趋势图与数据展示
- 推荐主方案：`fl_chart`
- 推荐理由：足够支撑趋势图、周报摘要与轻量统计展示
- 最佳搭档：主题 token、格式化器、空态与解释文案
- 备选方案：自绘图表
- 避免混搭：不要同时引入多套图表框架
- 接入注意事项：洞察页每个图形必须绑定一个业务结论，不做数据仪表盘堆叠
- 升级/维护风险：复杂图形交互增长时要控制 widget 复杂度

### 6.8 通用基础栈

- 能力域：国际化、模型生成、JSON 解析
- 推荐主方案：采用默认通用基础栈，不额外引入 `fpdart`
- 推荐理由：当前产品复杂度足以要求生成代码和 i18n，但还不需要全面函数式错误流
- 最佳搭档：`build_runner`
- 备选方案：在域规则显著膨胀后再增量引入 `fpdart`
- 避免混搭：不要一部分页面手写模型、一部分页面用生成模型
- 接入注意事项：修改 ARB 后必须重新生成本地化类
- 升级/维护风险：生成代码过期要通过 CI 或本地命令及时校正

## 7. 后端协作与接口契约要求

### 7.1 账号与权限模型

### 推荐方案

- 首发支持匿名本地态 + 登录增强态
- 登录后将本地记录与云端身份绑定
- 远端以单用户个人数据空间为主，不引入组织 / 多角色权限模型

### 备选方案

- 强制登录后才能进入核心链路
- 完全不做匿名身份绑定，仅在登录后新开账号空间

### 取舍理由

- PRD 强调降低首启门槛，强制登录会直接伤害激活完成率。
- 但匿名态不能无限放大，必须在同步、购买和换机恢复场景中有清晰绑定策略。

### 7.2 同步契约

- 客户端需要支持幂等上行，避免同一记录因重试重复写入。
- 同步对象至少包含：目标作息、睡眠记录、延迟原因标签、周报快照引用、会员快照关联信息。
- 每条同步对象需要稳定 `id`、更新时间、来源标记、删除 / 失效语义。

### 7.3 时间与时区契约

- 所有远端时间戳统一使用 UTC 存储。
- 业务展示与规则判断同时保留用户本地时区 / 记录时区信息。
- `GoalSchedule` 相关规则不能只存一个本地格式化时间字符串，必须保留可计算字段。

### 7.4 错误与重试契约

### 推荐方案

- 远端错误统一映射为有限项目内错误码：鉴权失败、权限不足、冲突、网络失败、超时、不可恢复服务端错误
- 同步链路支持指数退避与重试上限
- 会员与同步失败要分离，不互相阻断

### 备选方案

- 直接向上透传 SDK 原始异常

### 取舍理由

- 原始 SDK 异常不可直接暴露到应用层，否则业务状态会失控且难以国际化。

## 8. 数据与安全方案

### 8.1 推荐方案

- 健康原始数据最小化读取，只保留业务所需字段
- 本地敏感数据与普通业务数据分层存放
- 日志默认脱敏，不记录 token、原始会话、完整健康原始载荷
- 数据导出 / 删除路径至少在“我的”页可达

### 8.2 备选方案

- 为了排查问题长期保留完整原始健康载荷
- 将会话、用户标识、订阅快照混放在普通偏好存储中

### 8.3 取舍理由

- 该产品高度依赖用户信任，健康数据和作息行为天然敏感，设计上必须先收敛数据最小化原则。
- 调试便利不能凌驾于隐私边界之上。

### 8.4 安全边界

- `flutter_secure_storage`：会话、身份绑定、敏感票据
- `Drift`：结构化业务记录，必要时存脱敏引用
- `SharedPreferences`：仅非敏感标记
- 崩溃上报与日志：禁止直接上传个人睡眠原始记录全文

## 9. 埋点、监控与运营支持

### 9.1 埋点方案

### 推荐方案

- 以 PRD 的激活漏斗、行为闭环、商业化漏斗为第一版事件分类
- 事件名统一英文蛇形或下划线风格，属性命名稳定化
- 所有埋点在应用层或专用 analytics gateway 发出，不在 widget 树内散落

### 备选方案

- 先不上埋点，等功能都完成后再补
- 页面内直接调用多套分析 SDK

### 取舍理由

- PRD 已明确北极星指标与关键漏斗，不做埋点就无法验证商业假设。
- 但首发不必同时接入多套 SDK，可以先保留项目内事件网关与内存 / 控制台实现，再决定外部平台。

### 9.2 监控与告警

### 推荐方案

- 当前阶段先建立项目内日志与错误分类边界
- 预留生产崩溃监控接入口，等发布策略确认后接 `Sentry` 或 `Crashlytics`

### 备选方案

- 立即接入完整增长型 Firebase 监控栈
- 完全依赖用户反馈排查线上问题

### 取舍理由

- 当前 PRD 明确商业验证重要，但并未明确必须首发接入远程实验和完整增长平台。
- 因此先把事件 taxonomy、错误分类、监控装配点设计好，比仓促接入更多 SDK 更稳。

### 9.3 运营支持

- 若后续要求远程开关、灰度或 AB，建议在下一阶段明确是否引入 `firebase_remote_config`
- 周报生成、恢复建议、订阅权益同步等都需要可观测状态与人工兜底说明

## 10. 测试与质量保障

### 10.1 推荐方案

- 领域规则：单元测试
- provider / controller：应用层状态测试
- 页面关键状态：Widget 测试
- 插件边界：Fake / Mock 适配测试
- 主闭环：集成测试覆盖启动、目标设置、睡前进入、次日反馈、同步降级

### 10.2 备选方案

- 只做人工真机回归
- 只做纯单元测试，不覆盖页面状态矩阵

### 10.3 取舍理由

- 当前产品的风险主要来自状态矩阵和平台差异，而不是单一算法；只靠单元测试不够。
- 但首期也不需要为每个视觉细节上 golden 测试，先覆盖主状态矩阵更划算。

### 10.4 发布前检查

- `flutter gen-l10n`
- `dart run build_runner build --delete-conflicting-outputs`
- `flutter analyze`
- `flutter test`
- 真机验证：健康权限、通知调度、购买链路、小组件、登录

## 11. 实施计划与里程碑

### 11.1 里程碑建议

1. 全局技术基线确认
2. 模块拆分与模块级 RD
3. UI/UX 方向与冻结
4. Pencil 设计与架构映射
5. 功能实现与对齐验收
6. 商业化与发布准备

### 11.2 可并行流

- 客户端基础设施梳理：路由、主题、i18n、生成链路
- 数据与同步边界整理：Drift schema、同步队列、会话存储
- 商业化接入基线：会员状态模型、购买网关抽象
- 设计链路：UI 方向、冻结和 Pencil 源整理

### 11.3 阻塞项

- 未确认匿名策略与会员绑定策略前，不应固化登录 / 购买完整守卫
- 未确认是否首发引入远程配置前，不应锁死监控与发布栈
- 未完成模块拆分前，不应直接展开大面积页面实现

## 12. 风险清单与替代方案

### 12.1 技术风险

- 健康数据在不同平台上的可用性和延迟差异大
- 通知与小组件都存在明显平台差异
- 购买与身份绑定逻辑容易与匿名态冲突

### 12.2 协作风险

- 如果 PRD 后续临时把轮班 / 时差高级策略提前，会影响目标作息模型和模块边界
- 如果设计稿未覆盖空态、权限态和锁定态，后续实现会反复返工

### 12.3 发布风险

- 没有统一埋点 taxonomy，商业假设无法验证
- 没有明确数据删除 / 导出路径，会削弱隐私信任
- 购买、登录、通知等平台配置稍有遗漏就会卡发布

### 12.4 替代方案

- 若首发只做 iOS，可暂时降低小组件与登录渠道复杂度，但不改变总体架构基线
- 若首发暂不做远程实验，可保留本地开关与配置装配点，后续再接远程配置
- 若购买链路时间不足，可先完成会员状态展示和锁定入口，但必须保留真实网关边界，避免长期假数据占位

## 13. 模块拆分交接说明

供 `flutter-rd-module-splitter` 继承的全局结论如下：

- 保持项目主架构为 `lib/features/*`，不要在模块拆分阶段顺手推动全仓目录迁移。
- 启动分发统一由 `/launch` 承接，模块设计不得自行复制登录 / 首开守卫。
- 本地优先是硬约束：模块设计必须先定义本地可用状态，再定义同步增强状态。
- 用户可见文案必须走 Flutter 官方 l10n 链路，模块文档不要默认写死中文常量。
- 远端能力当前默认围绕 `supabase_flutter`，不要在模块级文档里擅自引入第二套网络主栈。
- 数据模型默认使用 `freezed` / `json_serializable`，不要在模块文档里回退到手写样板类。
- 设计链路上，任何显示层模块若引用 Pencil 或冻结设计源，后续实现必须以设计源为准。
- 模块拆分优先围绕业务闭环能力域，而不是围绕纯技术层切块。

## 14. 最终结论

### 推荐主方案

Rhythm 的全局技术基线应采用“本地优先 + Riverpod 注解状态栈 + GoRouter 启动分发 + Drift 结构化本地数据 + Supabase 增强同步 + 规则驱动商业闭环”的方案，并继续沿用当前仓库已建立的 `features/*` 边界。

### 为什么推荐这条路径

- 它与当前仓库事实一致，迁移成本最低。
- 它能覆盖 PRD 中最关键的激活、留存、恢复、订阅与信任要求。
- 它避免了“先铺大型通用基础设施、后发现首发并不需要”的过度设计。
- 它为后续模块拆分、设计冻结、Pencil 映射和实现阶段提供了稳定继承面。

### 不选的常见路径

- 不把产品直接建成“云端优先”工具，因为这与 PRD 的本地优先和低门槛激活冲突。
- 不在这一阶段引入新的主状态框架或第二套路由体系。
- 不把模块拆分、UI 细化和实现细节提前混入全局技术基线文档。

### 当前进入下一阶段前需确认的重点

- 是否认可“匿名可用、登录增强”的账号策略
- 是否认可“Supabase 为首发远端主栈，不额外预铺通用 REST 层”
- 是否认可“监控和实验能力先保留装配点，不强行首发接入完整增长栈”
- 是否认可下一步进入 `flutter-rd-module-splitter` 做模块级拆分
