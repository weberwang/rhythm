## 0. 文档定位

本文件用于把升级后的商业级 PRD 重新转成 Flutter 全局研发规划。它只负责全局技术基线，不负责详细模块拆分、UI/UX 设计稿、Pencil 复刻或代码实现。

后续模块拆分必须继承本文的架构、包栈、数据安全、埋点、发布和协作约束。

当前冻结设计源默认使用 `pen/v3.pen`。后续任何显示层设计、Pencil 对齐和实现准备，都以它作为唯一设计源，除非后续文档显式升级版本。

## 1. PRD 需求理解

### 1.1 产品目标

Rhythm 是作息行为管理 App，不是睡眠医学或助眠内容产品。首发目标是验证一条行为闭环：

`今晚提醒 -> 睡前收尾 -> 次日反馈 -> 原因标签 -> 恢复建议 -> 周复盘`

产品成功不取决于图表数量，而取决于用户是否持续完成“记录、理解、调整、恢复”的低负担循环。

### 1.2 目标用户

核心用户是 20-35 岁长期晚睡但想调整作息的人群，重点包含城市白领、远程办公/自由职业者、学生或年轻职场新人。首发不优先覆盖临床睡眠问题、硬件级监测、社交陪伴或泛健康内容需求。

### 1.3 关键业务目标

- 首次安装到首页可用时间不超过 2 分钟。
- 健康授权失败时仍可走手动记录闭环。
- 首页 3 秒内读懂昨晚结果和今晚目标。
- 睡前模式路径不超过 3 次点击。
- 付费墙只出现在高意图场景，不阻断激活。
- 免费层给结果，付费层给持续改善。

### 1.4 范围内能力

- 首次激活与引导
- 目标作息系统
- 健康数据接入与手动补录
- 今日反馈
- 睡前模式与提醒
- 日历热力图与原因标签
- 洞察、周报与恢复建议
- 账户、同步、隐私与数据
- 小组件与桌面存在感
- 会员基础版与付费墙
- 埋点、灰度、发布与运营监控

### 1.5 明确不做

- 医疗诊断、治疗、治愈类能力
- AI 聊天教练
- 社区内容流
- 情侣/朋友监督
- 深度医学睡眠评分
- 硬件联动
- 大量主题商店

## 2. 假设前提与待确认项

### 2.1 假设前提

- 首发允许匿名本地使用，登录用于云同步、换机恢复和会员状态。
- V0.1 优先验证核心闭环，V0.2 再强化恢复建议、会员和同步体验。
- 远端同步以 `supabase_flutter` 为主，不在 V0.1 另建独立 REST API。
- 健康数据接入通过 `health` 封装 HealthKit / Health Connect，手动记录是一等降级路径。
- 订阅能力通过 `purchases_flutter` 承接，Flutter 端只消费项目内部会员权益模型。
- 生产监控和远程配置暂不新增依赖，先通过应用内埋点网关和可替换接口保留扩展点。

### 2.2 待确认项

- 首发区域是中国区优先、英语区优先，还是中英双语同步。
- V0.1 是否上线真实 Apple / Google 登录，还是只保留入口并允许匿名优先。
- 是否需要在 V0.1 引入远程配置、A/B 和崩溃监控 SDK。
- 工作日/休息日双目标、轮班和时差模式是否进入 V1.0，还是继续后置。
- 会员定价采用低价高转化，还是中价位强调高级改善价值。

## 3. 业务流程与页面范围

### 3.1 主成功路径

1. 用户打开 App，进入激活引导。
2. 用户了解产品价值并选择登录或匿名继续。
3. 用户授权健康数据或选择手动记录。
4. 用户设置目标入睡、目标起床、熬夜阈值和提醒策略。
5. 用户进入今日页，看到今晚目标和睡前模式入口。
6. 到点后用户从通知、小组件或今日页进入睡前模式。
7. 次日用户看到结果反馈并补充原因标签。
8. 明显晚睡后用户看到恢复建议。
9. 一周后用户查看周报和稳定度趋势。
10. 用户在高意图节点遇到轻量付费承接。

### 3.2 异常路径

- 健康授权失败：进入手动记录路径，不阻断激活。
- 健康数据为空：提示数据可能延迟，提供补录入口。
- 网络不可用：本地核心闭环继续可用，同步和会员状态显示降级。
- 时区变化：暂停普通晚睡判断，提示用户确认目标策略。
- 订阅状态读取失败：不影响免费核心体验，会员能力暂按本地最近状态降级。

### 3.3 页面家族

- 全局与引导：启动分发、欢迎、登录、健康权限、目标设置、提醒策略、小组件引导、完成过渡。
- 一级主页面：今日、日历、睡前、洞察、我的。
- 二级页面：手动补录、周报详情、历史洞察、目标编辑、提醒设置、数据接入、账号同步、会员中心、隐私与数据、小组件与主题、时区与特殊模式。
- 覆盖层：时间选择、标签选择、恢复计划详情、稳定度说明、数据来源说明、权限补救、同步失败、删除账号、导出数据。

## 4. 总体技术架构

### 4.1 推荐方案

采用 `本地优先 + 轻量 DDD + feature-first + Riverpod 编排` 的 Flutter 架构。

分层：

- `app/`：启动、路由、全局装配、主题和启动守卫。
- `core/`：跨 feature 的时间、错误、分析、配置和基础设施适配。
- `shared/`：跨 feature 复用的展示组件和少量共享内核。
- `features/<feature>/domain`：实体、值对象、领域规则和仓储接口。
- `features/<feature>/application`：用例、状态聚合、Provider 和流程编排。
- `features/<feature>/data` 或 `infrastructure`：数据源、仓储实现、平台 SDK 适配。
- `features/<feature>/presentation`：页面、组件、弹层和用户交互。

推荐理由：

- PRD 需要离线可用、健康数据降级、手动修正和同步，必须避免 UI 直接持有平台 SDK。
- 作息目标、晚睡判断、稳定度、恢复计划等规则需要可单测。
- 商业级状态矩阵较完整，应用层需要清晰聚合 UI 状态。
- 后续设计稿、Pencil 和 Flutter 实现可以按 feature 独立推进。

### 4.2 备选方案

- 纯页面驱动架构：实现快，但会导致规则散落在页面和 Controller 中，不适合长期迭代。
- 重型 DDD：边界更严格，但对当前消费级 MVP 交付成本过高。
- 多 package monorepo：适合更大团队，当前阶段会增加工具链负担。

### 4.3 取舍结论

当前采用轻量 DDD，不追求复杂聚合根和领域事件，但必须保证领域规则、平台适配和展示层分离。

## 5. Flutter 客户端技术方案

### 5.1 状态管理与依赖组织

推荐方案：`hooks_riverpod` / `flutter_riverpod` + `riverpod_annotation` + `riverpod_generator`。

使用规则：

- 页面默认使用 `HookConsumerWidget`。
- Provider 默认用 `@riverpod` 注解生成。
- 页面只消费 ViewState，不直接访问 Repository 或平台插件。

备选方案：`bloc` 适合事件流更严格的团队，但会和当前项目依赖与已有实现不匹配。

取舍结论：继续沿用 Riverpod 注解生成，不引入第二套状态管理。

### 5.2 路由与入口守卫

推荐方案：`go_router`。

路由责任：

- 启动分发
- onboarding 完成状态
- 底部五个一级模块
- 通知、小组件、深链入口
- 会员付费墙和二级设置页

关键规则：

- 一级模块统一挂在 Shell 下。
- onboarding、付费墙、授权补救等独立路径不得复制底部导航。
- 通知和小组件入口先进入统一启动协调，再分发到睡前或今日页。

### 5.3 本地数据与结构化存储

推荐方案：`drift` + `sqlite3_flutter_libs` + Repository。

覆盖对象：

- 目标作息
- 睡眠记录
- 手动修正
- 原因标签
- 睡前会话
- 恢复计划
- 周报摘要
- 同步队列
- 小组件快照

备选方案：`shared_preferences` 仅用于轻量偏好，不适合承载业务数据。

取舍结论：结构化业务数据必须落 `drift`，敏感凭据落 `flutter_secure_storage`。

### 5.4 远端同步与账号

推荐方案：`supabase_flutter` + 本地同步队列 + 冲突策略。

原因：

- 当前项目已声明 Supabase。
- PRD 需要账号同步、换机恢复和订阅状态跨设备。
- V0.1/V0.2 不需要单独搭完整 REST 后端。

与 guardrail 的差异说明：

- 默认 HTTP 栈可保留 `dio + retrofit` 作为后续独立 API 方案。
- 当前阶段没有独立 HTTP API，直接新增 `dio/retrofit` 会形成未使用依赖。
- 若后续报告服务、运营配置或独立后端 API 成立，再按 guardrail 引入 `dio + retrofit`，并由 `core/network` 统一拥有。

### 5.5 健康数据与权限

推荐方案：`health` 封装 HealthKit / Health Connect。

接入规则：

- 平台 SDK 只出现在 data/infrastructure 层。
- 应用层只消费统一的健康权限状态和同步结果。
- 授权失败、平台不可用、无数据、同步失败必须区分。
- 手动补录和用户修正优先级高于系统原始记录展示。

### 5.6 提醒、时区和小组件

推荐方案：

- `flutter_local_notifications`：本地提醒
- `timezone` + `flutter_timezone`：时区感知调度
- `home_widget`：桌面小组件

接入规则：

- 提醒调度由 `notifications` 模块集中处理。
- 小组件只能输出低敏快照，不输出原始健康细节。
- 通知和小组件点击统一进入入口控制器，不在平台层直接跳业务页面。

### 5.7 会员与订阅

推荐方案：`purchases_flutter` + 项目内部 `MembershipEntitlement`。

接入规则：

- UI、应用层、领域层不直接依赖 Purchases 原始类型。
- 付费墙由 `MembershipPaywallPolicy` 判断触发上下文。
- 付费墙不得阻断首次激活、目标设置、记录补录、今日页和首周洞察首屏。

### 5.8 图表与可视化

推荐方案：`fl_chart` + 自定义轻量图形组件。

适用：

- 趋势图
- 原因分布
- 稳定度摘要

热力图建议使用自定义 Flutter 布局实现，不强行套通用图表库。

### 5.9 国际化、文案和合规

推荐方案：Flutter 官方 `gen_l10n` + `intl`。

规则：

- 新增用户可见文案先写 `app_en.arb`，再同步中文。
- 业务层不承载最终展示文案。
- 全站避免“治疗、诊断、治愈、医学改善、精准评估失眠”等表达。

### 5.10 模型与代码生成

推荐方案：

- 领域模型、DTO、ViewState 优先使用 `freezed_annotation`。
- JSON DTO 使用 `json_annotation`。
- Provider 使用 `@riverpod`。
- 统一通过 `build_runner` 生成。

禁止：

- 长期手写 `copyWith`、相等性和 JSON map 转换。
- 手改 `.g.dart` 和 `.freezed.dart`。

## 6. 第三方包选型与最佳搭配

| 能力域 | 推荐主方案 | 最佳搭配 | 避免混搭 |
| --- | --- | --- | --- |
| 状态与依赖 | `hooks_riverpod` / `flutter_riverpod` | `riverpod_annotation` + `riverpod_generator` | `provider`、`bloc`、`get_it` 同职能并存 |
| 路由 | `go_router` | 启动守卫、通知入口、小组件入口 | 多套路由系统 |
| 本地结构化数据 | `drift` | `sqlite3_flutter_libs` + Repository | 用 `shared_preferences` 存业务记录 |
| 敏感存储 | `flutter_secure_storage` | 会话、令牌、敏感绑定信息 | token 存普通偏好 |
| 健康数据 | `health` | 平台权限网关 + 手动降级 | UI 直接调健康 SDK |
| 通知与时区 | `flutter_local_notifications` | `timezone` + `flutter_timezone` | 多个提醒调度入口 |
| 小组件 | `home_widget` | 快照服务 + 隐私过滤 | 小组件输出过细健康数据 |
| 账号同步 | `supabase_flutter` | 本地同步队列 + 冲突策略 | UI 直接拼远端写入 |
| 会员 | `purchases_flutter` | 内部权益模型 + 付费策略 | 页面直接依赖 Purchases 类型 |
| 图表 | `fl_chart` | 自定义热力图和趋势组件 | 为热力图引入复杂新库 |

| 代码生成 | `freezed` + `json_annotation` | `build_runner` | 手写样板和生成混用 |

## 7. 后端协作与接口契约

### 7.1 推荐方案

首发后端协作以 Supabase 为主，业务核心本地优先。

远端职责：

- 账号绑定和会话恢复
- 睡眠记录、目标、标签、周报摘要同步
- 会员权益状态同步
- 换机恢复
- 后续报表服务或运营配置预留

Flutter 本地职责：

- 核心闭环可离线运行
- 本地写入先进同步队列
- 冲突策略优先保护用户手动编辑
- 网络失败不阻断今日、睡前、补录和基础周报

### 7.2 契约要求

- 所有时间戳统一保存 UTC，同时保存用户业务时区。
- `recordDate` 按用户“一天起始时间”计算。
- 同步写入必须具备幂等键。
- 远端错误需要映射为项目内部错误类型。
- 隐私、导出、删除账号必须有清晰接口或人工流程占位。

### 7.3 备选方案

后续如果独立后端能力增强，可引入 REST API：

- `dio + retrofit` 负责 HTTP 声明。
- Supabase 退为身份或存储底座。
- 远端报表、A/B、运营配置由独立服务管理。

当前不推荐立即采用该方案，避免在 V0.1 前引入未使用的网络层复杂度。

## 8. 数据与安全方案

### 8.1 数据分级

| 数据 | 存储 | 安全要求 |
| --- | --- | --- |
| 登录令牌、敏感会话 | `flutter_secure_storage` | 不进日志，不进普通偏好 |
| 睡眠记录、目标、标签、周报 | `drift` | 本地优先，可同步，来源可追溯 |
| 语言、主题、onboarding 状态 | `shared_preferences` | 非敏感轻量偏好 |
| 小组件快照 | `home_widget` 存储 | 只输出低敏摘要 |

### 8.2 隐私原则

- 最小权限读取健康数据。
- 明确说明读取范围和用途。
- 日志和埋点不包含原始入睡/起床时间等敏感细节。
- 用户修正数据不得覆盖原始系统记录，保留来源可解释性。
- 账号删除和数据导出路径首发即具备说明入口。

## 9. 埋点、监控与运营支持

### 9.1 埋点分类

- 激活：打开、开始引导、登录、授权、目标设置、提醒设置、完成引导。
- 行为：进入睡前、选择状态、点击动作、同步记录、手动补录、补标签。
- 反馈：查看今日、查看日历、查看周报、查看恢复计划。
- 商业化：付费墙曝光、来源、试用、购买、恢复购买、取消。
- 信任：隐私页、数据导出、账号同步、权限补救。

### 9.2 监控建议

V0.1 可先保留统一分析网关，后续按需要接入生产 SDK。

待确认是否引入：

- Crash 监控
- 远程配置
- A/B 实验
- 灰度开关

如果引入，必须有事件字典、fallback 默认值和关闭开关。

- 集成测试：首次激活到今日页、睡前模式到次日反馈、周报生成、同步降级。

## 12. 风险与替代方案

| 风险 | 影响 | 主方案 | 替代方案 |
| --- | --- | --- | --- |
| 健康数据授权率低 | 激活受损 | 强化授权前信任说明 | 手动记录作为一等路径 |
| Android Health Connect 差异 | 数据质量不稳 | 平台状态分级和降级 | 首发先弱化 Android 自动读取 |
| 同步复杂度高 | 发布延期 | 本地优先 + 队列渐进 | V0.1 只做本地，V0.2 同步 |
| 付费过早损伤留存 | 激活下降 | 高意图节点再拦截 | 先只展示会员入口 |
| 设计稿与实现冲突 | 返工 | 先设计冻结再实现 | 记录缺口后回设计流程 |
| 医疗化表达风险 | 合规风险 | 文案规则和扫描 | 高风险文案下线 |

## 13. 模块拆分交接说明

模块拆分必须继承：

- 本地优先架构。
- Riverpod 注解生成。
- GoRouter 单一路由树。
- Drift 结构化业务数据。
- Supabase 作为首发同步底座。
- Purchases 只通过内部会员模型暴露。
- 健康、通知、小组件 SDK 只落在 data/infrastructure 边界。
- 付费墙不得阻断首次核心体验。
- 设计稿进入实现前必须经过设计冻结，并以 `pen/v3.pen` 完成 Pencil 核对。

模块拆分不得重新选择包栈，也不得在模块层新增全局架构方案。若出现新的全局包或后端决策，必须回到本文件更新技术基线。

## 14. 最终结论

推荐主方案是：以当前 Flutter 工程为基础，按本地优先、轻量 DDD、feature-first 和商业状态矩阵重新组织后续研发。升级后的商业 PRD 不要求推倒现有工程，但要求后续所有模块都重新继承商业目标、状态矩阵、付费边界和设计冻结流程。

下一步进入 `flutter-rd-module-splitter`，生成模块索引、模块详情卡、模块依赖图，以及每个模块成对的 UI/UX RD 和实现 RD。
